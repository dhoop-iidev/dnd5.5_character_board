# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Goal

A personal digital "playboard" for playing one **D&D 2024** character (the "5.5" rules, **System Reference Document 5.2.1**) at the table: stats in panes, quick rules reference, live effects and rests, and rule checks that flag an illegal or inconsistent build. Sibling of the 3.5 playboard (`../../D&D 3.5/dnd3.5_playboard`), from which only rules-agnostic code was copied. It is a living spec; update this file as decisions are made.

The app is generic: any SRD 5.2.1 species, background and class (12 classes, one subclass each); a character is created or imported on the welcome screen. No character ships with the app. Pure SRD for now: `docs/house-rules.md` starts empty (user decision 2026-10-25). Exception, house rule #3 (2026-10-29): a **custom background** (`backgroundId: 'custom'`, `Background.custom`: name, three abilities, two skills, a tool; any SRD Origin feat; 50 GP), built by `model/customBackground.ts` `backgroundDef` into an ordinary `BackgroundDef`: always look a background up through `backgroundDef`, never `rules.backgrounds.get`. Picked in `ui/CustomBackgroundEditor.svelte` (welcome screen and Origin block). Non-SRD backgrounds (2024 PHB, fan wikis such as 5point5.fandom.com, which hosts Unearthed Arcana playtest versions) are not used. House rule #4 (2026-10-29): **custom feats** the player enters (`Character.customFeats`, ids `custom-feat-<n>`, their own summary + book and page in `Source.book`, prerequisites, +1 choices, optional modifiers), edited in `ui/CustomFeatsEditor.svelte` under the progression; `model/customFeats.ts` `withCustomFeats` merges them into a per-character copy of the rules (feats + `feat:<id>` effects), called by `compute` and `validate`. House rule #5 (2026-10-29): **custom subclasses** (`Character.customSubclasses`, ids `custom-subclass-<n>`, features `<class>:<subclass>:f<n>` with the player's summary, optional uses/activation/named options/modifiers, always-prepared spells by class level), edited in `ui/CustomSubclassesEditor.svelte` under the custom feats, exported/imported as `*.subclass.json` (`kind: 'custom-subclass'`); `model/customSubclasses.ts` `withCustomSubclasses` adds them to their class. House rule #6 (2026-10-29): **custom species** (`Character.customSpecies`, ids `custom-species-<n>`, traits `<species>:t<n>` from a character level (`SpeciesTraitDef.level`, filtered in `sheet/build.ts`), optional Darkvision/other speeds/skills/resistances/uses/activation/modifiers, no ability increases), edited in `ui/CustomSpeciesEditor.svelte` under the custom subclasses, exported/imported as `*.species.json` (`kind: 'custom-species'`); `model/customSpecies.ts` `withCustomSpecies`. `model/custom.ts` `withCustom` applies the three merges and is what `compute`, `validate` and `view.rules` use. In the UI, list feats, subclasses and species from `view.rules`, never the global `rules`. No non-SRD text is ever written in the repo. Tier 3 (2026-10-29): subclass spellcasting (`SubclassDef.spellcasting`, block kind `'subclass'`, `SpellcastingBlock.list` = the list it casts from; its multiclass share only as the player enters it, check `subclass-multiclass-<class>`), weapons created by a feature (`EffectDef.weapon`, virtual `ItemInstance.feature`, uid `feature:<owner>`, never saved, not counted against hands), Wild Shape changes (`EffectDef.wildShape` formulas, `engine/companions.ts` `wildShapeLimitsFor(sheet)`: use it instead of `wildShapeLimits`), creatures from the player's book (`Companion.custom`, `model/customCreature.ts`, `ui/CustomCreatureForm.svelte`). Player formulas: `model/formula.ts` ("13 + wis", "5 + rangerLevel*5", "druidLevel/3").

## Hard rules

- **D&D 2024 rules (SRD 5.2.1) only.** Never 3.5 and never the 2014 rules (SRD 5.1): no race/subrace (2024 = species), no plain Inspiration (2024 = Heroic Inspiration), no ki points (Focus Points), no 2014 feat or class table. No 3.5 mechanic of any kind (the test below lists them). `src/__tests__/no-35.test.ts` fails the build on 3.5 and 2014 vocabulary in `src/`, `docs/` and `examples/` (EN and FR); a legitimate hit is allowed by ending its line with `no35-ok`. no35-ok
- Rule base = SRD 5.2.1 + the DM exceptions in `docs/house-rules.md`. Anything that isn't plain SRD (other books, interpretations) must be in that file with status `confirmed` before it is implemented.
- Authority order when a rule seems ambiguous: the SRD 5.2.1 text itself (Rules Glossary wording wins over a looser phrasing elsewhere) → official 2024 errata and the Sage Advice Compendium (2024) → the 2024 Player's Handbook / DMG if the user owns them. Record the answer with sources in `docs/rules/rulings-*.md`. **Never implement a rule assumption the SRD doesn't back without asking the user first**; if the books genuinely don't answer, stop, explain the options, add a `pending` entry to `docs/house-rules.md`. Questions about the character's own facts always go to the user.
- Every rule, feat, item, class feature and computed formula carries a `source`: the SRD 5.2.1 **page** (English PDF) and `frPage` (official French PDF), plus the section heading. Popups show "SRD 5.2.1 p. 29 / FR p. 30", the English part linking to the cited paragraph of https://5e24srd.com (`src/data/links.ts`), so the user can show the DM proof.
- The SRD is **CC-BY-4.0**: its text may be quoted verbatim, in English and in the official French translation, as long as `public/CC-BY.txt` (the attribution statement) ships with the app and is linked in the footer. Nothing from non-SRD books.
- Weights store both units (`lb`, `kg`) and distances both (`ft`, `m`), **as printed in the French SRD** (no conversion house rule; the pipeline checks the printed pairs and logs mismatches). Show lb/ft in English and kg/m in French.
- Every piece of user-facing text is trilingual (EN, FR, ES): `{ en, fr, es }`, never one language hard-coded. Use the official 2024 terms of `FR_SRD_CC_v5.2.1.pdf` (e.g. "Maîtrise", "Avantage", "test d20", "aptitude de classe", "repos court", "espèce", "historique", "don") and `SP_SRD_CC_v5.2.1.pdf` (e.g. "Bonificador por competencia", "Ventaja", "Descanso corto"); look terms up in the generated data.

## Platform & stack

- Offline web app installable on a tablet (PWA): Vite + Svelte 5 + TypeScript, no backend, any modern browser, touch-friendly.
- State is saved in the browser and moved between PC and tablet by exporting/importing a JSON file (`edition: "srd-5.2.1"`, versioned `schemaVersion`; `model/migrate.ts` converts older versions and refuses 3.5 files).
- Python (miniforge, `C:/Users/le_re/miniforge3/python.exe`) is only for the data pipeline in `tools/` (pymupdf reads the PDFs), never for the app.

## Architecture principles

- **Data-driven:** classes (per-level tables), subclasses, species, backgrounds, feats with machine-readable prerequisites, weapons (properties, mastery), armor, gear, spells, conditions, magic items and beasts live in bilingual JSON (`src/data/srd/*.json`, generated), typed by `src/data/types.ts` (the contract shared with the Python pipeline). Hand-written data goes to `src/data/custom/`.
- **Character = choices + levels:** the build is a level-by-level record (class, subclass, HP roll or average, feat or Ability Score Improvement, class-feature choices); everything else is derived. Species, background (ability +2/+1 or +1/+1/+1, Origin feat, skills, tool), proficiencies and inventory are stored once.
- **Computed with breakdown:** every derived value (AC, attacks, damage, saves, skills, passive checks, HP, initiative, speed, spell save DC, carrying capacity) is a `Stat { total, parts }` with each `Part { sourceId, label, value, effectName?, source }`. Popups show this list, so the calculation and the explanation never disagree.
- **Stacking (Rules Glossary):** 2024 has no typed modifiers. Numbers add up, except: effects with the **same name** don't stack (the best applies), only one AC base formula applies, Advantage/Disadvantage are booleans that cancel each other and never stack, temporary HP don't add up. `engine/stacking.ts`.
- **Core invariants (2026-10-30, after the Spells tab stopped opening):**
  - _Owners:_ every feature, trait, feat and option the character has is an `Owner` with a unique id. A repeatable feat taken again is `feat:<id>@<where>` (`feat:magic-initiate@human:versatile`), reading the same effect (`effectId`); the background's copy stays `feat:<id>`. `Owner.feat` says where a feat comes from (background, level, granting feature).
  - _One choice store (schema 5):_ every feature, trait and option choice is in `Character.featureChoices`, keyed `<owner id>` or `<owner id>#<choice id>` (`choiceKey`): Fighting Style (a feat id), Divine Order, invocations, open Expertise (`rogue:expertise`), etc. A feat's own choices stay in its `FeatPick` (background, level, `extraFeats[<granting owner>]`). `LevelEntry.choices` and `Character.expertise` are gone (`model/migrate.ts` moves them). The engine applies a value only while its owner exists; a level's feat only on an Ability Score Improvement row.
  - _Cleanup:_ after a structural change (a level's class, subclass or feat, a level removed, species, background), `model/reconcile.ts` removes choices of owners the character lost (run by `state.svelte.ts`; never on load or import, where leftovers show as `choice-stale-` / `feat-stale-` warnings).
  - _Warnings:_ `RuleWarning.ownerId` / `choiceId` / `value` say what a warning is about; the progression row and the tab are read from these (`ui/progression.ts`, `ui/spellChoices.ts`), never parsed from the id. `validate()` makes ids unique (they are list keys).
  - _Tests:_ `engine/__tests__/invariants.test.ts` (unique owner ids, warning ids and listed values at every level of every example, fresh characters and messy saves; compute/validate don't change the character); `ui/__tests__/panes.dom.test.ts` mounts the app with Svelte's browser runtime (happy-dom, Vitest project `dom`) and visits every tab, level row and `<details>`, which catches duplicate `{#each}` keys and state written while rendering (the server-side `render.test.ts` can't). Display-only lists use index keys, never display text.
- **Engine layout:** `engine/compute.ts` runs the stages of `engine/sheet/` in order (build → modifiers → core → defense → skills → attacks → spells → classes → assemble); `engine/validate.ts` runs the checkers of `engine/checks/`. **Validation = warnings, never blocking.**
- **Effects:** an active effect (condition, spell, feature, item) is a set of changes; conditions and Exhaustion levels are data. Rests (`engine/rests.ts`): Short Rest spends Hit Dice and resets short-rest resources; Long Rest restores HP, all Hit Dice and all resources, ends Temporary HP (SRD p. 185, p. 18).
- Model each rule from the SRD text first (cite page + section in a code comment or the data), then encode it. When a rule is unclear, ask; don't guess.

## Commands

- `npm run dev` / `npm run build` / `npm run check` (svelte-check + tsc) / `npm test` (Vitest: projects `node` and `dom`; one project: `node node_modules/vitest/vitest.mjs run --project dom`) / `npm run format`.
- `python tools/build_data.py`: regenerates `src/data/srd/*.json` from `sources/` (see `tools/README.md`); `python tools/validate_data.py` and `python tools/cross_check_md.py` must pass before a commit.
- **Gotcha:** the `&` in the folder path (`D&D 5.5`) breaks npm's Windows `.cmd` shims; the npm scripts call `node node_modules/<pkg>/…` directly. Keep it that way, don't use `npx`.
- Deployment: pushing to `main` runs `.github/workflows/deploy.yml` (tests, build, GitHub Pages). `base: './'`, installable offline PWA.
- `examples/` holds fictional legal builds; `examples.test.ts` keeps them warning-free. `character_saves/` is gitignored: never commit it.
